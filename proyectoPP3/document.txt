1. DESCRIPCIÓN GENERAL
--------------------------------------------------------------------------------
El proyecto es una aplicación web separada en tres capas:

- Backend: API HTTP en Node.js (módulos ESM) con persistencia en SQLite.
- Frontend: aplicación Web Components con patrón MVC (Modelo, Vista, Controlador).
- Testing: pruebas unitarias y de integración ejecutadas con node:test.

El backend usa el módulo nativo node:sqlite y expone procedimientos por HTTP.
El frontend consume esos procedimientos mediante POST y muestra una interfaz en
español. Todo el código fuente (archivos, funciones y variables) está escrito en
inglés; los textos visibles para el usuario permanecen en español.

Estructura general:

  backend/

2. BACKEND
--------------------------------------------------------------------------------

2.1 backend/server/database.js
--------------------------------------------------------------------------------
Archivo de conexión única a SQLite.

- Importa DatabaseSync de node:sqlite.
- Crea la instancia db apuntando a ./db.sqlite3.
- Exporta db por defecto.

Esta conexión es compartida por los repositorios que trabajan con SQL.


2.2 backend/server/main.mjs
--------------------------------------------------------------------------------
Punto de entrada del servidor HTTP.

Funciones:

- defaultConfig()
    Devuelve la configuración por defecto: IP 127.0.0.1, puerto 3000,
    defaultPath del frontend y ruta de la base de datos.

- loadConfig()
    Lee backend/configure/config.json. Si falla, registra el error y usa
    defaultConfig().

- connectDb(path)
    Resuelve la ruta de la base de datos y devuelve una instancia DatabaseSync.

- requestDispatcher(req, res)
    Recibe cada petición HTTP. Construye la URL, configura las cabeceras CORS,
    responde 204 a OPTIONS, busca la ruta en el router y responde 404 si no
    existe. Si la ruta es pública, ejecuta el handler. Si es privada, valida la
    sesión con getSessionFromRequest, autoriza con authorize y responde 401 o
    403 cuando corresponde. Finalmente ejecuta el handler.

- start()
    Se ejecuta cuando el servidor queda escuchando. Muestra la URL de la API y
    la ubicación del frontend.

Flujo de arranque:

  1. Carga la configuración.
  2. Conecta la base de datos.
  3. Crea el Map del router.
  4. Registra las rutas con setupRoutes.
  5. Crea el servidor HTTP y escucha en la IP y puerto configurados.

2.5 backend/handlers
--------------------------------------------------------------------------------

2.5.1 availabilityHandler.js
--------------------------------------------------------------------------------
Handlers de disponibilidad y reservas.

Funciones auxiliares:

- isValidTime(time)
    Valida el formato HH:MM entre 00:00 y 24:00.

- readBody(req)
    Acumula el cuerpo de la petición y lo devuelve como texto.

- readJson(req)
    Convierte el cuerpo en JSON. Si no es válido lanza BusinessError 400.

- respondJson(res, statusCode, object)
    Escribe una respuesta JSON con el código indicado.

- respondError(res, error)
    Si el error es BusinessError usa su status; en cualquier otro caso responde
    500 y registra el error en consola.

- validateResource(resource)
    Verifica que el recurso exista en la tabla resource.

- isAdmin(session)
    Devuelve true si el usuario tiene permiso sobre /api/reservations/cancel.

- whoReserves(session, indicatedName)
    Define el nombre de la reserva: el administrador puede indicar otro nombre;
    un usuario común reserva siempre a su propio nombre.

- normalizeFinalState(blocks)
    Valida la lista de bloques, descarta los libres, elimina duplicados por
    dateTime y ordena el resultado.

Handlers exportados:

- getAvailabilityHandler(req, res)
    Lee resource, startTime y endTime. Valida el recurso y las horas. Devuelve
    status success con data.startTime, data.endTime, data.intervalDuration y
    data.occupiedZone.

- applyReservationHandler(req, res)
    Recibe el estado final de bloques de un recurso. Compara con lo guardado:
      * Bloques nuevos: requieren sesión, no pueden ser del pasado y se agregan.
      * Bloques que faltan: requieren sesión, no pueden ser del pasado; solo el
        administrador o el dueño de la reserva pueden liberarlos.
      * Sin cambios: responde que no había cambios.
    Guarda los bloques en JSON y sincroniza la tabla reservation. Si falla la
    base de datos, restaura el JSON anterior.

- releaseReservationHandler(req, res)
    Compatibilidad para liberar bloques por lista de dateTime. Valida recurso y
    bloques, rechaza horarios pasados, guarda el nuevo estado y elimina las
    reservas de la base de datos.

2.7.3 ScheduleManager.js
--------------------------------------------------------------------------------
Lógica de negocio de disponibilidad. No accede a archivos ni a la base de datos.

- BusinessError
    Error de negocio con código HTTP (por defecto 400).

- constructor()
    Define START_HOUR = 6, END_HOUR = 24 y MINUTES_PER_BLOCK = 30.

- pad(num)
    Rellena con cero a la izquierda.

- formatDateTime(date)
    Devuelve "AAAA-MM-DD HH:MM".

- generateTimeBlocks(day)
    Genera todos los bloques de 30 minutos de un día, desde las 06:00 hasta las
    24:00. Cada bloque tiene dateTime, occupied y teacher.

- applyReservation(dayBlocks, startTime, endTime, teacher)
    Marca como ocupados los bloques que caen dentro del rango.

- mergeBlocks(oldBlocks, newBlocks)
    Fusiona bloques por dateTime; los nuevos reemplazan a los viejos.

- buildNewBlocks(dateTimes, teacher)
    Construye la grilla de cada día y devuelve solo los bloques reservados.

- currentBlockStart(now)
    Devuelve el inicio del bloque de 30 minutos que contiene a "now".

- isPastBlock(dateTime, now)
    Indica si un bloque es anterior al bloque actual.

- hasPastBlock(blocks, now)
    Indica si alguno de los bloques es del pasado.

- isValidResource(resource)
    Comprueba que el recurso exista en la base de datos.

- isValidDateTime(dateTime)
    Valida formato, fecha real (rechaza 2026-02-31), hora entre 06:00 y 24:00 y
    múltiplos de 30 minutos.

- normalizeBlocks(dateTimes)
    Valida la lista y elimina duplicados.

- checkAvailability(savedBlocks, dateTimes)
    Devuelve disponible o el primer conflicto encontrado.

- reserve(savedBlocks, dateTimes, teacher)
    Valida disponibilidad y devuelve la lista fusionada y ordenada.

- release(savedBlocks, dateTimes)
    Quita los bloques indicados y devuelve { blocks, released }.

- buildRawResponse(savedBlocks, startTime, endTime, day)
    Devuelve los bloques ocupados para el frontend con las claves startTime,
    endTime, intervalDuration y occupiedZone.


2.7.4 login.js
--------------------------------------------------------------------------------
- login(username, password)
    Busca el usuario, valida la contraseña con bcrypt, obtiene sus grupos y crea
    o reactiva la sesión en userSessions. Devuelve status, result y description.


2.7.5 register.js
--------------------------------------------------------------------------------
- registrationError(message, status)
    Crea un Error con código HTTP.

- register(username, password)
    Valida tipos, longitud de usuario (3 a 30) y contraseña (mínimo 4). Verifica
    que el usuario no exista y que exista el grupo profesor. Crea el usuario y
    lo asigna al grupo profesor dentro de una transacción.


2.7.6 sessions.js
--------------------------------------------------------------------------------
- userSessions
    Map en memoria con las sesiones activas por id de usuario.


2.8 backend/data
--------------------------------------------------------------------------------
Archivos JSON de disponibilidad por recurso:

  calculadora.json
  computadora.json
  impresora.json
  proyector.json
  teclado.json

Cada archivo contiene una lista de bloques con:

  dateTime: fecha y hora del bloque.
  occupied: true si está reservado.
  teacher: nombre del docente que reservó.

Los archivos se leen y escriben con blocksRepository.js.

6. BASE DE DATOS
--------------------------------------------------------------------------------
Tablas principales:

- user: usuarios con username único y password hasheada.
- group: grupos de permisos.
- members: relación usuario-grupo.
- endpoint: rutas protegidas.
- access: relación grupo-endpoint.
- status: estados de gestión y conservación.
- resource: inventario de recursos.
- loan: préstamos.
- reservation: historial de reservas por bloque.

Relaciones:
- Un usuario puede pertenecer a varios grupos.
- Un grupo puede tener acceso a varios endpoints.
- Un recurso puede tener varias reservas y varios préstamos.
- Cada reserva pertenece a un recurso y a un usuario.
